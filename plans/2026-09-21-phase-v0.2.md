# Phase v0.2 Plan: Plans and Notes

## Goal
Implement Phase v0.2 of ClassQue covering lesson Plans (`PLN-001` through `PLN-009`) and quick-capture Notes (`NOT-001` through `NOT-008`), alongside verifying module toggles (`SET-005`) for Plans and Notes. The phase delivers structured plan authoring driven dynamically by Subject Packs (Generic and English), plan attachment/reuse across sessions, one-handed mobile note taking linked to sessions, groups, or individual learners, and print-optimized views.

---

## Requirement IDs in Scope

### Plans Module (`docs/05-modules/plans.md`)
- **PLN-001**: Plans list tab with newest-updated sorting, limit 50 with cursor pagination, title substring search, subject pack filtering, archived toggle, and session usage count display.
- **PLN-002**: Create and edit Plan with title (1–120 chars) and dynamic content sections based on the Subject Pack's template (`text` up to 4000 chars, `list` up to 30 items of 200 chars, `pairs` up to 60 term/definition rows), validated by pack-generated Zod schemas for both Generic and English packs.
- **PLN-003**: Attach/detach a Plan to a Session from Session detail, setting `sessions.plan_id` and marking the session as an exception (`is_exception = 1`).
- **PLN-004**: Duplicate a Plan with translated title suffix (`{title} (copy)`), setting `source_plan_id`; support one-step "Reuse plan from an earlier session" attaching the duplicate to the current session.
- **PLN-005**: Detect when an edited Plan is attached to multiple Sessions (tested with 3+ sessions), prompting the teacher to choose between "Edit for all" or "Duplicate and edit".
- **PLN-006**: Soft-archive and restore Plans (`archived_at`), ensuring attached sessions retain the relationship and display an "Archived" tag without hard deleting.
- **PLN-007**: Enforce `visibility = 'private'` on all Plan records per DM-007.
- **PLN-008**: Dedicated print-friendly single-Plan view using `@media print` formatted for A4, hiding app navigation and interactive controls.
- **PLN-009**: Unsaved Plan form drafts persist locally in `localStorage` and warn on unsaved exit.

### Notes Module (`docs/05-modules/notes.md`)
- **NOT-001**: Quick-capture floating "Add note" trigger on Today, Session detail, Group detail, and Learner profile, opening a compact sheet with prefilled context.
- **NOT-002**: Enforce target invariant that a Note must attach to at least one of Session, Group, or Learner; auto-populate `group_id` when adding from Session; body length 1–2000 characters.
- **NOT-003**: Paginated list of Notes (limit 50, cursor, newest first) filterable per Learner, per Group, or per Session.
- **NOT-004**: Edit note body and hard-delete note with confirmation dialog.
- **NOT-005**: Attaching a Note to a Session marks that Session as an exception (`is_exception = 1`) per DM-023.
- **NOT-006**: Note drafts persist locally in `localStorage` until saved or dismissed.
- **NOT-007**: Global recent Notes screen under More → Notes showing chronological feed with contextual tags (Group name, Learner name, date).
- **NOT-008**: Enforce `visibility = 'private'` on all Note records per DM-007.

### Settings & Cross-Cutting Invariants
- **SET-005**: Verify that disabling Plans or Notes in module toggles completely hides their navigation and UI entry points and results in zero network requests to their API endpoints.
- **DM-001**: Tenant isolation via `account_id` on all `plans` and `notes` queries and mutations.
- **DM-002**: ULID generation in the Worker using `generateId()`.
- **DM-003**: ISO-8601 UTC timestamps for `created_at` and `updated_at`.
- **DM-005**: Archive for Plans (`archived_at`), hard delete for Notes (`DELETE`).
- **DM-023**: Mark session as `is_exception = 1` on Plan attach/detach and Note addition.
- **H9**: Learner privacy protection — zero logging of note content/body or learner names, and no inclusion of Notes in any export.

## Migrations

The migration file `migrations/0003_phase_v0_2.sql` will execute the exact four-step sequence required by `docs/02-domain-model.md` and `docs/ddl_ref.md`:

```sql
-- Step 1: CREATE TABLE plans first so it exists as an FK target
CREATE TABLE plans (
  id TEXT PRIMARY KEY,
  account_id TEXT NOT NULL REFERENCES accounts(id),
  pack_id TEXT NOT NULL,
  pack_version INTEGER NOT NULL,
  title TEXT NOT NULL,
  content TEXT NOT NULL DEFAULT '{}',
  visibility TEXT NOT NULL DEFAULT 'private' CHECK (visibility IN ('private')),
  source_plan_id TEXT REFERENCES plans(id),
  archived_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX idx_plans_account ON plans(account_id, archived_at, updated_at);

-- Step 2: CREATE TABLE notes
CREATE TABLE notes (
  id TEXT PRIMARY KEY,
  account_id TEXT NOT NULL REFERENCES accounts(id),
  session_id TEXT REFERENCES sessions(id),
  group_id TEXT REFERENCES groups(id),
  learner_id TEXT REFERENCES learners(id),
  body TEXT NOT NULL CHECK (length(body) BETWEEN 1 AND 2000),
  visibility TEXT NOT NULL DEFAULT 'private' CHECK (visibility IN ('private')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  CHECK (session_id IS NOT NULL OR group_id IS NOT NULL OR learner_id IS NOT NULL)
);
CREATE INDEX idx_notes_learner ON notes(account_id, learner_id);
CREATE INDEX idx_notes_group ON notes(account_id, group_id);
CREATE INDEX idx_notes_session ON notes(account_id, session_id);

-- Step 3: ALTER TABLE sessions to add plan_id FK reference
ALTER TABLE sessions ADD COLUMN plan_id TEXT REFERENCES plans(id);

-- Step 4: CREATE INDEX on sessions(account_id, plan_id)
CREATE INDEX idx_sessions_plan ON sessions(account_id, plan_id);
```

## Risks

- **SQLite Foreign Key Ordering during Migration**: SQLite enforces foreign keys strictly. If `ALTER TABLE sessions ADD COLUMN plan_id REFERENCES plans(id)` executes before `CREATE TABLE plans`, the migration fails. Mitigation: Migration `0003` strictly adheres to the four-step sequence specified in `docs/02-domain-model.md`.
- **Dynamic Pack Validation Edge Cases**: If a Group's pack is changed or unknown keys exist in stored Plan JSON, strict Zod parsing could fail. Mitigation: Use `.passthrough()` on plan content schemas to preserve unknown or legacy keys read-only without data loss (PK-003).
- **Privacy Leaks (H9)**: Accidental logging of note body text during D1 queries or debug statements. Mitigation: Strict code review and test assertions ensuring only row counts and execution metrics are logged.
- **Local Storage Draft Collisions**: Notes and Plans drafts colliding when multiple tabs or entities are opened. Mitigation: Key drafts by entity type and ID (e.g., `draft:plan:${id || 'new'}` and `draft:note:${contextKey}`).

## Assumptions Made

- For `PLN-005`, "Used in {count} sessions" check calculates count based on `sessions.plan_id = plans.id` within the same account.
- When choosing "Duplicate and edit" for a Plan from within a Session context, the newly created duplicate is automatically attached to that Session, leaving the original Plan attached to the remaining sessions.
- Indonesian translation keys for new module strings follow the standard glossary terms (`Rencana` for Plan, `Catatan` for Note) and will be added to both `en.json` and `id.json`.
- In accordance with D-016, Plan printing relies on native browser `window.print()` and CSS print stylesheets, without any server-side PDF generation.
