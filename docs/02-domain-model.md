# 02 — Domain model

## Hierarchy

```
Account (tenant; one per teacher in the MVP)
 ├─ User(s) via Membership (role: teacher only in MVP)
 └─ Workplace (institution | independent)
     ├─ Term (institution only, optional)
     ├─ Grading settings (pass mark, letter bands, CEFR bands)
     ├─ Learner (belongs to exactly one Workplace)
     └─ Group (class | individual; uses one Subject Pack; optional Term)
         ├─ Group–Learner membership (many-to-many, dated)
         ├─ Schedule rule → generates Sessions
         ├─ Session → Attendance, Plan (optional), Notes
         └─ Assessment → Scores
Progress Level: per Learner per Skill, dated
Note: attached to a Session, Group and/or Learner
```

## Global rules
- **DM-001** Every tenant table has `account_id`. A child row's `account_id` MUST equal its parent's; the service layer enforces this on write.
- **DM-002** IDs are ULID `TEXT`, generated in the Worker.
- **DM-003** Timestamps `created_at` / `updated_at` are UTC ISO-8601 `TEXT`.
- **DM-004** Session date/time are stored as **local wall-clock** (`session_date`, `start_time`) plus IANA `tz`, because "10:00 Tuesday class" is a local concept. Derive UTC instants only when needed.
- **DM-005** Archive vs delete: Workplace, Term, Group, Learner, Assessment, Plan use `archived_at` (never hard-deleted in the MVP). Notes, Attendance rows and Scores may be hard-deleted by the user. Archived items are hidden from pickers by default and visible under an "Archived" filter with Restore.
- **DM-006** Enumerations are enforced by `CHECK` constraints and mirrored as Zod enums in `src/shared/schemas/`.
- **DM-007** Future-readiness fields (`role`, `visibility`) exist now and are set to their single MVP values (`teacher`, `private`). Do not build UI or logic that branches on other values.

## Tables (DDL reference)

Write these as forward-only migrations (Phase 0 creates the identity tables, later phases add the rest). Column order is not significant; names, types and constraints are.
[read docs/ddl_ref.md (non-optional), omitted here to avoid character limit]

**Circular reference & SQLite migration approach:** `sessions.plan_id` references `plans(id)`, which arrives in Phase v0.2. In SQLite/D1, `ALTER TABLE ADD COLUMN` with a foreign key constraint is valid only when the referenced table already exists and the column is nullable with default NULL. Therefore:
1. In the Phase v0.1 migration (`0002`), create `sessions` **without** `plan_id`.
2. In the Phase v0.2 migration (`0003`), create `CREATE TABLE plans (...)` **first** so the target table exists.
3. Immediately after in the same migration file, execute `ALTER TABLE sessions ADD COLUMN plan_id TEXT REFERENCES plans(id);` and `CREATE INDEX idx_sessions_plan ON sessions(account_id, plan_id);`.
Keep the column definition in `ddl_ref.md` as the target schema state.
 
## Invariants (enforced in services, covered by tests)
- **DM-010** A Group's Workplace never changes after creation. A Learner belongs to exactly one Workplace, and can only join Groups in that Workplace.
- **DM-011** `term_id` on a Group is allowed only when its Workplace `kind = 'institution'` and the Term belongs to that Workplace.
- **DM-012** A Group of `kind = 'individual'` has exactly one active Group–Learner membership.
- **DM-013** Attendance rows are valid only for Learners with an active membership on the Session's date: `joined_on <= session_date` and (`left_on IS NULL` or `left_on >= session_date`).
- **DM-014** Assessments: `max_score` is required for `numeric` and must be `NULL` for `cefr`. A Score's `value_num` requires `0 <= value_num <= max_score`; `value_level` must be a level of the CEFR scale.
- **DM-015** Assessment `type_key` and `skill_key` must exist in the Group's Subject Pack.
- **DM-016** Progress Levels are always recorded in a Group context (`group_id` required). `skill_key` and `scale_key` must be defined by that Group's Subject Pack. A Learner's profile shows the latest level per skill across all their Groups.
## Session generation
- **DM-020** Sessions are materialized from Schedule rules for a rolling window: from `max(today, rule.starts_on)` to `min(rule.ends_on, term.ends_on if any, today + 56 days)`.
- **DM-021** Generation is idempotent via `uq_sessions_rule_slot` (`INSERT OR IGNORE`). The client calls `POST /api/v1/schedule/top-up` at most once per local day (stored in `localStorage`) and after any rule change.
- **DM-022** Editing a rule regenerates only future sessions with `status = 'scheduled'` and `is_exception = 0`, in one `db.batch`.
- **DM-023** A session becomes `is_exception = 1` when the teacher edits its time/room, attaches a Plan, adds a Note to it, or changes its status manually. Exceptions are never deleted or regenerated by rule edits.
- **DM-024** Rescheduling creates a new session (`rescheduled_from_id` = old id) and sets the old one to `rescheduled`. Cancelling sets `cancelled`. Saving attendance on a `scheduled` session sets it to `held` (the UI offers undo).
- **DM-025** Overlap detection is computed at read time in shared code (same account, same `session_date`, intersecting `[start_time, start_time + duration)`), comparing wall-clock times in the user's timezone. Overlaps are warnings, never blockers.
